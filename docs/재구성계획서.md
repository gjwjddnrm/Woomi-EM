# Woomi-EM 재구성 계획서

- **대상:** `Mandooegg/herring` 브랜치 (커밋 `e6c32bf`) — https://github.com/gjwjddnrm/Woomi-EM/tree/Mandooegg/herring
- **작성일:** 2026-11-20
- **근거:** 3자 코드 리뷰(내부·Codex·Antigravity) + 실제 브라우저 레드팀 실측
- **원칙:** **서버 없음 · 정적 단일 파일 배포(GitHub Pages) · 오프라인 동작 · 클라이언트 암호화**라는 현재 장점은 그대로 유지하고, 그 안에서 안전성과 유지보수성만 끌어올린다.

> ⚠️ **대전제 — 현장 데이터 호환성**
> 이미 여러 현장 PC의 브라우저 안에 암호화된 실제 자료가 쌓여 있습니다(localStorage `fireplan_*`·`woomi_sec_meta_v1`, IndexedDB `fireplan_b3a_db`·`fireplan_hotwork_db`·`fireplan_b56_db`). **어떤 재구성도 이 저장 형식을 깨면 현장 자료가 전부 사라집니다.** 모든 단계는 "기존 암호화 자료를 그대로 읽어 들일 수 있는가"를 통과 조건으로 둔다.

## 1. 현재 구조 진단

### 1.1 빌드·소스 구조
- 본체가 거대한 단일 HTML 두 개(`src/교육훈련_원본.html` 10,256줄, `src/화기작업_원본.html` 903줄)이고, 수정 내용이 **파이썬 문자열 치환 패치 13개**(`build/patch_*.py`, 약 2,000줄)로 원본에 덧씌워진다.
- 패치가 **앞선 패치가 삽입한 문자열을 다시 치환**하는 자기참조·순서 의존 구조라, 원본 공백 하나만 바뀌어도 빌드가 깨진다. 문법 검사·자동완성·스택 추적이 모두 무력화된다.
- 라우터가 3개 화면(`#form/byeolji-3-1`, `#hotwork`, `#form/byeolji-5`)만 열어 주는데, **쓰지 않는 화면 20여 개와 318KB짜리 base64 로고 2장**이 그대로 배포된다(결과물의 약 40%).
- 화기작업 앱은 base64로 인코딩돼 `<script type="application/octet-stream">`에 담겨 `iframe.srcdoc`로 디코딩된다. 격리(`sandbox`) 이점은 없이 복잡도만 늘린다.
- 저장·PDF 생성·서명 처리·IndexedDB 래퍼가 3개 화면에 **중복 구현**되어, 한쪽 버그 수정이 다른 쪽에 반영되지 않는다.
- 자동 테스트·CI가 전혀 없다.

### 1.2 저장·암호화 구조
- 모든 기록을 **단일 IndexedDB 키에 통짜 JSON 암호문**으로 저장한다. 저장할 때마다 전체 배열을 복제→직렬화→단일 AES-GCM 버퍼로 암호화→덮어쓴다. 기록이 쌓이면 메모리 피크가 수 배로 커지고, 한 번의 쓰기 오류가 전체 기록을 파괴할 수 있다.
- 비밀번호 변경 시 수백 개 기록을 한꺼번에 재암호화하는데 **원자적이지 않아**(중간 중단 시 키 불일치) 영구 복호화 불가 위험이 있다.
- 탭 간 동기화(`BroadcastChannel`/`storage` 이벤트)가 없어 두 탭이 서로 덮어쓴다.
- AES-GCM에 레코드 이름을 AAD로 묶지 않아 암호문 위치 바꿔치기를 탐지하지 못한다.

### 1.3 레드팀 실측으로 확인된 취약점(별도 PDF 보고서 참조)
| 심각도 | 항목 | 라이브 |
|---|---|---|
| 치명 | PDF 글자 경유 XSS로 임의 코드 실행 | 재현됨 |
| 치명 | 조작된 `.woomi` 백업으로 브라우저 ~60초 정지(DoS) | 재현됨 |
| 높음 | 비밀번호 대입 지연이 새로고침으로 초기화 | 재현됨 |
| 높음 | 잠금 상태에서 현장명·관리자 실명 평문 노출 | 재현됨 |
| 높음 | 비밀번호 없이 전체삭제 도달 | 재현됨 |
| 높음 | 교육일지 기록 유실 / 백업 복원 덮어쓰기 | 코드상 위험(미재현) |

## 2. 목표 아키텍처

유지(변경 없음): 정적 단일 `index.html` 배포 · GitHub Pages · 오프라인 · 클라이언트 AES 암호화 · 비밀번호 잠금.

바꾸는 것:
1. **소스 모듈화** — 기능별 표준 JS/CSS 모듈로 분리.
   ```
   src/
     sec/            잠금·암호화·백업 (현 sec-*.js 정리)
     shared/         idb.js · crypto.js · pdf.js · sig.js · escape.js · darkmode.js
     forms/
       edu/          교육·훈련(별지 3-1·3-2)
       inspect/      안전점검(별지 5·6)
       hotwork/      화기작업(별지 7·8)
     app/            라우터·레이아웃·부팅
   ```
2. **번들러 도입(esbuild 또는 Vite + vite-plugin-singlefile)** — 개발 시 모듈·린트·소스맵, 배포 시 지금과 똑같은 **단일 정적 `index.html`**. `patch_*.py` 치환 파이프라인은 제거.
3. **공통 모듈화** — 저장·PDF·서명·이스케이프·다크모드 방어를 한 벌로 합쳐 중복 제거.
4. **저장·암호화 고도화** — 기록 단위 개별 암호화 + AAD 바인딩, 사진은 별도 스토어. 비밀번호에서 유도한 키로 **데이터 키(DEK)만 감싸는 키 래핑** 구조 → 비밀번호 변경이 메타 1건 교체로 원자화.
5. **XSS 차단** — 모든 `innerHTML` 동적 값 이스케이프 또는 `textContent`/DOM API, 필터는 항상 정화(가능하면 DOMPurify). CSP에서 `'unsafe-inline'` 제거.
6. **공급망 제거(선택)** — 외부 라이브러리를 저장소에 직접 호스팅 + Service Worker 캐시 → CSP를 `'self'`로 조이고 완전 오프라인화.
7. **멀티 탭 조정** — `BroadcastChannel`로 잠금·비밀번호 변경·저장 충돌 감지.
8. **테스트/CI** — 암호화·백업·파서·이스케이프 단위 테스트 + 레드팀 시나리오를 Playwright 회귀 테스트로 고정.

## 3. 단계별 실행 계획

각 단계는 **독립적으로 배포 가능**하도록 쪼갠다. **구조 정리(1단계)를 먼저 해 코드를 깨끗이 한 뒤, 그 위에서 보안·데이터 수정(2단계)을 한다** — 지금처럼 파이썬 치환 패치로 보안을 고치면 그 자체가 불안정하기 때문이다.

### 0단계 — 안전망 구축 (예상 1~2일, 선행 필수)
- 현재 `index.html`과 `src`+`patch` 빌드 결과가 **바이트 단위로 같은지** 확인하는 스크립트.
- 기존 저장 형식(localStorage 키·IDB 이름·암호문 포맷·`.woomi` 백업 포맷)을 **"호환성 계약" 문서로 고정**.
- 레드팀 7개 시나리오를 현재 `index.html` 대상 **자동 회귀 테스트**로 변환(이후 모든 단계에서 재실행).
- **통과 조건:** 빌드 일치 확인 + 테스트 그린 + 호환성 계약 문서 완성.

### 1단계 — 패치 병합 + 죽은 코드 제거 (예상 2~3일) ★구조 정리의 근본
- `patch_*.py` 13개의 결과를 `src`에 **1회 영구 반영**, 치환 파이프라인 종료 → "원본 공백 하나에 빌드가 깨지는" 문제 해소.
- 도달 불가능한 화면 20여 개·318KB base64 로고·`exam/`(별도 저장소/페이지로 분리) 제거.
- README를 현재 제공 서식(별지 5·6 포함)과 수정 방법에 맞게 갱신.
- **통과 조건:** 빌드 결과의 기능 동일성(회귀 테스트) + 결과물 용량 축소 확인. → **main 병합·배포**.

### 2단계 — 보안·데이터 수정 (정리된 소스 위에서, 예상 2~4일) ★안전 확보
- XSS 차단: 모든 `innerHTML` 동적 값 이스케이프, 필터 항상 정화.
- `.woomi` 복원 시 `iter` 상·하한 검증(DoS 차단).
- 대입 지연을 저장소에 기록해 새로고침에도 유지.
- 전체삭제 전 강한 확인 추가, 삭제가 다른 탭에 막히면 성공 처리하지 않게 수정.
- 평문 메타: 실명 암호화 또는 README를 실제와 일치하도록 수정.
- 데이터 유실 치명 2건(기록 로드 경쟁·복원 덮어쓰기) 정밀 재현 후 수정.
- **통과 조건:** 레드팀 회귀 테스트에서 재현 항목이 모두 OK로 전환 + 기존 자료 정상 열람. → **main 병합·배포**.

### 3단계 — 모듈화 + 번들러 전환 (예상 3~5일)
- `src`를 2장 구조대로 모듈 분리, 중복 코드(저장·PDF·서명·이스케이프) 통합.
- esbuild/Vite(singlefile) 도입 → 산출물은 동일한 단일 `index.html`.
- 인라인 `onclick` → `addEventListener`로 이전하고 CSP에서 `'unsafe-inline'` 제거.
- 화기작업을 CSS 스코핑(또는 Shadow DOM)으로 통합, `iframe srcdoc`+base64 이중 패킹 제거.
- **통과 조건:** 회귀 테스트 그린 + 기존 자료 호환 + 단일 파일 배포 동작.

### 4단계 — 저장·암호화 아키텍처 (예상 1~2주) ★최고 위험
- 기록 단위 개별 암호화 + 사진 별도 스토어, 모든 암호문에 스토어·키 이름 AAD 바인딩.
- DEK/KEK 키 래핑 구조로 전환 → 비밀번호 변경 원자화, 변경 중 유실 위험 제거.
- `BroadcastChannel` 멀티 탭 조정.
- **기존 단일키 암호문 → 신규 구조 마이그레이션 로직** + 실패 시 롤백.
- **통과 조건:** 기존 형식으로 저장된 실제 모양의 자료를 신규 구조로 무손실 이전하는 마이그레이션 테스트 통과(이것이 전체에서 가장 중요한 관문).

### 5단계 — 완전 오프라인 + CDN 제거 (예상 3~5일, 선택)
- pdf.js(워커 포함)·tesseract(+WASM·언어 모델)·html2canvas·jspdf·jszip를 `/vendor/`에 고정 버전으로 직접 호스팅 + Service Worker 캐시.
- CSP에서 `https://cdn.jsdelivr.net` 제거, `'self'`만 허용.
- **통과 조건:** 네트워크 차단 상태에서 PDF 읽기·OCR·PDF 저장 동작.

## 4. 위험 관리

| 위험 | 영향 | 완화 |
|---|---|---|
| 저장 형식 변경으로 현장 자료 유실 | 치명 | 0단계 호환성 계약 고정 · 4단계 무손실 마이그레이션 테스트 · 배포 전 백업 유도 |
| 재구성 중 회귀 | 높음 | 모든 단계 레드팀+기능 회귀 테스트 통과를 병합 조건으로 |
| 패치 병합 중 기능 누락 | 중간 | 2단계 빌드 결과 동일성 검증 후에만 진행 |
| 일정 지연 | 중간 | 1단계(보안)를 재구성과 분리해 먼저 배포, 현장 안전 확보 |

**롤백:** 각 단계는 독립 배포이므로, 문제 시 직전 `main` 커밋으로 되돌리면 현장은 즉시 이전 동작으로 복구된다(자료는 호환성 유지로 보존).

## 5. 우선순위 요약

1. **0단계(안전망)** — 선행 필수. 호환성 계약과 회귀 테스트가 이후 모든 작업을 지킨다.
2. **1단계(패치 병합·죽은 코드 제거)** — 구조 문제의 근본. 저위험이며 이후 작업의 토대이자 보안 수정을 깔끔하게 만든다.
3. **2단계(보안·데이터 수정)** — 정리된 소스 위에서 라이브 취약점 해결 후 배포.
4. **3단계(모듈화·번들러)** — 유지보수성 핵심.
5. **4단계(저장·암호화)** — 가장 큰 위험이자 가장 큰 구조 개선, 마이그레이션 검증에 시간을 넉넉히.
6. **5단계(오프라인·CDN 제거)** — 현장 인터넷 환경 보고 선택.

> 보안 수정(2단계)을 무거운 재구성(3~4단계) 뒤로 미루지 않는 이유: 라이브로 터진 취약점이 현장 실명·연락처·서명·사진에 직결되고, 수정 자체는 작기 때문이다. 1단계로 구조만 먼저 정리하면 그 수정이 "불안정한 치환"이 아니라 "일반 코드 수정"이 되어 안전해진다.

> 일정 수치는 모두 추정이며, 실제 코드 상태와 현장 배포 제약에 따라 조정이 필요합니다.
